# iPhone 15 Pro：本轮效率修改与测量范围

目标是让相同画面与任务使用更少的处理时间。构建成功只证明包可构建及校验，
不能证明手机帧率提升。既有日志是旧版本样本，不能当作构建 21/22 的设备对照。

## CPU：分离无关等待队列

原同步实现把所有 WebAssembly 地址的等待者放在同一队列、同一互斥锁内。
图形通知、资源读取和游戏任务互相争用该锁；通知还会扫描其他地址的等待者。
新版按真实共享内存地址分到 64 个桶，桶按 128 字节对齐。相同地址的 32/64 位
等待及不同包装对象的别名仍汇合，通知的精确数量、超时和重查协议保留。

校验包括持有 A 桶的锁时 B 桶仍能处理通知、竞态唤醒、别名、越界及超时。
构建机用相同编译选项和请求/应答程序，在 ABBA 顺序下对比构建 21 原始源码
与新版。基线源码哈希固定，报告原始样本、CPU 时间、墙钟时间和吞吐。
这是同步子系统的测量，不能直接换算为全游戏 CPU 或 FPS 改善。

## GPU：按视图复制深度代理

Metal 需要深度格式进行比较采样，因此渲染器会为某些普通浮点贴图创建深度代理。
原实现一旦失效，就复制整个贴图的所有 mip 与数组层。当前 SRV 可能只暴露其中
一部分。新版保持相同底层贴图与着色器，按 SRV 范围复制，记录每个子资源的有效性。
每次原图写入后全部失效；后续不同视图会补齐其范围，不读取未准备的内容。

CPU 图像夹具检查分片、立方体范围、重复读取、失效及对象替换。可选 Metal 探针
使用相同浮点到深度复制路径，比较全部视图与一个立方体视图：候选验证前先将
代理清为零，防止错误地继承基线路径的正确像素。逐像素核对来源和基线结果。
探针记录复制工作量、CPU 编码时间及可用的 GPU 时间戳。无 Metal 设备明确跳过，
不会给出虚构的 GPU 百分比。手机日志的复制量计数保持启动以来累计，避免跨
报告窗口的分片复制被误算为收益。

没有改动图形质量、盲目丢弃渲染附件、延迟遮挡查询或加入插帧。原源码已有立即
提交查询优于延迟提交的历史记录，因此本轮保留该行为。

实际分包来源：https://github.com/alihammoud21/playgta5/releases/tag/full-game-v1

仓库中的引擎与当前客户端完全匹配：
11ca8d2c04c5e843d18ff4aea4899d72c86973c6b031df334e67c446b2ae83e0。
游戏清单的 5814 条路径均在镜像中；两个解析器 HTML 各差两字节，其余大小匹配。
这两项不在本轮修改的渲染资源内，未用它们覆盖用户现有文件。

按范围取出 country_05 的 cs5_1/2/3 与 v_trees.rpf，合计 132184064 字节。
四个文件均与仓库清单 SHA-256 相符。样本内 41 个 YTD 共解析 1027 张纹理：
BC1 879、BC3 140、BC5 4、BC2 3、A8 1；最大边长 1024，通常带多级 mipmap。
这些结果只代表样本，不是全地图审计。YDR 仅做目录统计，没有把文件名中的
LOD 字样当作完整几何层级验证。

重新压缩容器主要影响磁盘和读取；改变贴图尺寸、几何或距离会涉及画质取舍。
目前先实施上述不减少画面需求的客户端修改，保留原有游戏文件。
